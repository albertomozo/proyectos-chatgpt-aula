**Versión:** 0.1 · **Fecha:** 23/11/2026 · **Estado:** BORRADOR DE PARTIDA  
**Modalidad:** caso didáctico con datos de partida ficticios  
**Responsable de la copia:** PENDIENTE alumno o equipo

## Naturaleza del ejemplo

Este es un caso nuevo preparado para practicar. No reproduce documentos aprobados ni hechos comprobados de otro proyecto. Los datos siguientes definen el supuesto de partida; las aprobaciones, pruebas y resultados deben producirse durante la actividad y quedar identificados. Un resultado simulado se marca como tal.

## Situación de partida

En un aula ficticia de formación hay 12 puestos informáticos. Las incidencias se comunican de palabra o mediante mensajes dispersos. Se pierde información, se repiten avisos y resulta difícil saber qué problemas siguen abiertos. El equipo quiere probar un sistema sencillo para comunicar y registrar incidencias.

| Dato | Propuesta inicial del caso |
|---|---|
| Denominación oficial | INCIDENCIAS AULA |
| Destinatarios | Alumnado que comunica incidencias y docente que revisa el registro |
| Objetivo preliminar | Construir y probar un formulario conectado a un registro donde cada aviso pueda identificarse y consultarse |
| Producto mínimo | Formulario, registro centralizado, referencia de incidencia, confirmación y una prueba documentada del flujo |
| Criterios a concretar | Campos necesarios, unicidad de referencia, acceso al registro, contenido de confirmación y muestra de pruebas |
| Herramientas candidatas | Google Forms y Google Sheets; selección y comprobación pendientes, sin obligación de usar automatización de pago |
| Recursos de práctica | Una persona o equipo con navegador; acceso a cuentas y permisos por comprobar |
| Duración propuesta | 3 sesiones de 2 horas; disponibilidad y viabilidad por validar con el docente |
| Fechas absolutas | PENDIENTES; definir según calendario real de la actividad |
| Presupuesto objetivo | Sin gasto adicional; licencias, límites y costes indirectos pendientes de comprobar |
| Roles | Alumno o equipo prepara; docente revisa. Nombres y autoridad didáctica de aprobación por confirmar |
| Metodología | Kanban sencillo; columnas y WIP a proponer según capacidad |
| Exclusiones iniciales | Aplicación móvil propia, reparación de equipos, integración corporativa y despliegue con datos personales reales |
| Restricciones | Usar datos de prueba ficticios; no poner contraseñas ni información personal en el formulario |
| Evidencias a producir | Documento de acta y alcance, cronograma y capturas o registros de las pruebas realizadas |
| Aprobaciones y resultados | No constan al inicio; no hay tareas ejecutadas acreditadas |

## Preguntas de arranque

1. ¿Qué campos necesita una incidencia para poder atenderla?
2. ¿Qué herramienta puede generar la referencia sin duplicados y cómo se comprobará?
3. ¿La confirmación será en pantalla, por correo o ambas, y qué exige cada opción?
4. ¿Quién debe ver el registro y quién puede modificarlo?
5. ¿Qué entregable cabe completar en el tiempo real disponible?
